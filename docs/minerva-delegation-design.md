# Делегирование Minerva: внутренние дети и агенты OpenIDEA

Решение по повторному исследованию 26 ноября 2026 года. Дополняет
[minerva-subagents.md](minerva-subagents.md). Это контракт реализации, а не

## Уточнения после исследования Orca

Ниже — наши решения по её аналогии, а не описание уже реализованной Minerva.
Orca координирует полноценные движки, в том числе structured chat без терминала.
Поэтому executor адресуется через устойчивую связь, а не номер панели или PID.
Её CLI и терминальный транспорт в Minerva не переносим: используем AgentManager.

### Задание, попытка и живой исполнитель

Связь delegation описывает ребёнка; work item описывает задание; activation —
одну попытку задания. Work item имеет собственный ID, spec и результат, не равен
IDE task ID (диалогу). Повтор после сбоя сохраняет work item, но получает новую
activation. Новое поручение тому же ребёнку создаёт новый work item и activation.
Минимальный старт создаёт эти записи одной операцией; отдельный DAG UI не нужен.

Отчёт несёт work item ID и activation ID; сервис проверяет отправителя, активную
попытку и принадлежность заданию. Повтор того же result ID идемпотентен. Поздний
отчёт старой попытки остаётся в аудите, но не завершает новое задание и не меняет
его статус. Аналогично старый heartbeat не продлевает жизнь новой activation.

Храним независимо outcome попытки, validation результата и liveness исполнителя
(`live`, `exited`, `unknown`). Принятый отчёт не доказывает выход процесса;
остановка/потеря связи не означают успешный результат. При `unknown` запрещён
автоматический fallback, который мог бы создать второго пишущего исполнителя.
Очистка ресурсов проверяет их владельца и подтверждение остановки; закрытие UI
не считается остановкой. Архив истории сохраняется после освобождения ресурсов.
Слот выполнения освобождается при подтверждённом окончании activation, а не
обязательно выходе всего процесса: idle executor может остаться для reuse.
Его удержание учитывается отдельным лимитом resident-ресурсов. Нельзя закрывать
общий процесс, который обслуживает другие задания, или удалять внешнюю историю.
Основа разделения — [Orca worker teardown](https://github.com/stablyai/orca/blob/afcbcf4a45a8a1ae621d7d39604961311cf474e7/skill-guides/orchestration/references/worker-teardown.md).

### Доставка и продолжение

У inbox один авторитетный потребитель с сохраняемым поколением. Переподключение
того же владельца сохраняет неподтверждённую доставку; передача координации
увеличивает поколение и запрещает старому владельцу читать/подтверждать сообщения.
Запись входящего notice в родительский canonical session event log и ack выполняются
в одной транзакции repository в mh-sessions. Ack подтверждает сохранение, не
потребление моделью; binding в следующий run и защита branch head описаны в плане.
Внешняя история AgentManager в эту транзакцию
не входит: сохраняем ссылку и ограниченный итог, не копируем внешний журнал.
Событие UI — уведомление об этой записи, а не ack.
Пробуждение родителя идёт через существующую очередь запусков, не через второй
параллельный Rig loop. Переполнение inbox, размер отчёта и контекстный бюджет
ограничены; большие результаты хранятся по ссылке с коротким summary.

`send` возвращает фактическую квитанцию: сообщение поставлено в очередь текущей
попытки, передано как steer, либо принято как новое поручение. Для завершённого
поручения последнее требует admission новой activation и поддержки выбранного
режима продолжения. Живой idle executor допускает reuse без требования resume;
возобновление закрытой сессии требует resume capability. Свежая сессия с summary
допустима только при явном разрешении вызывающего. Квитанция указывает reuse,
resume или fresh-with-summary и фактический адрес; недоступный вариант отклоняется.
Завершённый результат прежнего поручения не переписывается.

### Вопросы, зависимости и минимальный объём

Вопрос ребёнка имеет correlation ID и привязку к activation; ответ получает
тот же исполнитель. Таймаут вопроса — явный исход ожидания, не согласие.
Вопрос не расширяет permissions: запрос разрешения проходит политику OpenIDEA.
Отдельный decision gate нужен для блокировки следующего задания до решения
координатора/пользователя, а не для имитации паузы уже работающего движка.

В MVP включаем идентификаторы задания/попытки, fencing потребителя, квитанции send,
неопределённую liveness и вопросы. DAG scheduler, массовые адресаты, удалённые
хосты и автоматические worktrees — последующие потребители того же сервиса.
При будущем DAG успешное выполнение исследования не равно положительной
проверке: зависимость с требованием качества открывается по validation/gate.
Эти правила принадлежат coordinator/service и repository, а не tool handler/UI.

## Граница плагина

Встроенный Rust-плагин `tool-subagent` предоставляет инструменты модели. Он не
является устанавливаемым MH-пакетом, MCP-сервером или вторым агентным циклом.
Его жизненный цикл принадлежит embedded runtime Minerva. Пользовательский менеджер
плагинов и отдельный механизм skills для этого не возвращаются.

Разделяем три обязанности:

1. **Tool adapter:** схемы, разбор аргументов, обращение к сервису, результат запуска.
2. **Delegation service:** дерево, admission, слоты, activation, ожидания, inbox/outbox
   и координация исполнения. Хранилище вызывается через порт.
3. **Execution adapters:** существующий Minerva/Rig runtime либо сервис задач
   OpenIDEA для полноценного внешнего агента.

Инструмент не читает SQLite, не запускает CLI и не обращается к frontend store.
Сервис не рисует UI и не реализует OAuth или provider wire formats.

## Два вида исполнителя

Нельзя объединять engine и LLM provider в одну строку. Пример формы запроса
(иллюстрация контракта, не готовая публичная JSON Schema):

```ts
type Target =
  | { kind: "minerva"; route?: string; effort?: string }
  | { kind: "ide-agent"; agentId: string; options?: Record<string, string> };
```

Для Minerva route — актуальный `api:<provider>/<model>`, в том числе подписка
Codex внутри Rig. Для `ide-agent` agentId берётся из реестра OpenIDEA: native
Codex, Claude Code, ACP и другие установленные движки. Его options проверяет
адаптер по реальным config options; общий runtime не переводит effort наугад.
Наличие AgentManager.prompt(now=true) не доказывает steer: этот метод может
перейти к очереди и отмене текущего хода. Порт возвращает реальный режим доставки.

У каждой связи есть delegationId, parent/root session ID, engine, activationId
и адрес исполнителя. Внутренний адрес — Minerva session ID; внешний — project ID,
IDE task ID и внешний session ID, если адаптер действительно его предоставляет.
Полная история внешнего движка остаётся у OpenIDEA/его адаптера; в родительский
контекст приходит ограниченный итог со ссылкой на исходную историю.

## Протокол и обеспечиваемые возможности

Единые операции: discover, start, list, wait, send, interrupt. Но доступность
send/steer/resume/fork/effort/read-only/depth control объявляется исполнителем.
Unsupported — явная ошибка до запуска, а не успешный no-op. DSH one-shot external
backend не считаем основанием объявлять наши native adapters однократными:
способности проверяются отдельно через существующий OpenIDEA контракт.

Контекст вызова устанавливает caller session/run/call ID, cwd и актуальную
политику. Модель не выбирает произвольного отправителя или чужой root. Resume
проверяет принадлежность ребёнка; self-target, ancestor-target и циклы ожидания
отклоняются. Выбор route/engine проходит текущий allowlist и capability preflight.

Запуск резервирует слот, сохраняет связь и activation, публикует событие ребёнка,
затем запускает исполнителя. Инструмент возвращает подтверждение принятия,
не итог. Ресурс starting учитывается в лимите. Каждый внешний запуск получает
operation ID; повтор запроса не создаёт второго CLI/task.

Итог и квитанция доставки сохраняются атомарно в outbox. Повтор доставки возможен,
но один result ID принимается родителем один раз. Успешное завершение не равно
прохождению проверки результата: execution status и validation status отдельны.

Отмена tool-call до публикации отменяет старт и освобождает резерв. После
публикации activation живёт независимо от завершённого tool-call. Обычный Stop
родителя сохраняет детей; Stop tree и shutdown останавливают дерево. Для внешнего
движка состояние stopping не заменяет подтверждение фактического завершения.

Нельзя считать delegation безопасным ReadOnly-инструментом только по
`ToolDefinition.side_effect = false`: он должен отдельно проверять реальные
полномочия дочернего исполнителя. Движок без подтверждённого ограничения записи
не допускается в ReadOnly-задание. Дочерние политики не шире родительских.

Fallback до старта допустим в явно разрешённой цепочке. После возможной записи
сначала подтверждаем остановку и исход, затем решаем о новом исполнителе.
Внешние потомки движка входят в наблюдаемое дерево лишь при поддержке адаптера;
скрытую рекурсию нельзя выдавать за соблюдённый общий лимит глубины.

## Владение кодом

Пути ниже — целевая раскладка, создаются по мере реализации, без пустых заглушек.

| Место                                                | Ответственность                                                                             |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `vendor/minerva/crates/plugin-sdk/src/delegation.rs` | Нейтральные DTO, capabilities и единственное объявление ExecutionPort, без Rig/IDE/UI/SQL   |
| `vendor/minerva/crates/delegation/`                  | Сервис, admission, scheduler, доставка и RepositoryPort; ExecutionPort импортируется из SDK |
| `vendor/minerva/plugins/tool-subagent/`              | Регистрация инструментов и тонкие handlers                                                  |
| `vendor/minerva/plugins/mh-sessions/src/delegation/` | Транзакции SQLite, связи, operation IDs, inbox/outbox                                       |
| `vendor/minerva/crates/runtime/src/delegation.rs`    | Composition root: установка сервиса, портов и инструментов                                  |
| `crates/ide-agent/src/delegation/`                   | Адаптер к AgentManager, capabilities, project/task ownership                                |
| `crates/ide-agent/src/native/minerva/delegation.rs`  | Перевод событий в существующую модель дочерних сессий OpenIDEA                              |

Существующий граф `mh-agent-loop -> mh-plugin-manager` нельзя замкнуть обратной
зависимостью tool-плагина на AgentLoopService. Плагин устанавливается composition
root после публикации исполнителя и получает executor port. Обратные ссылки
реестра инструментов/исполнителя используют weak handles; shutdown сначала
снимает регистрацию, прекращает admission и завершает свои activation.

Хост-мост вызывает AgentManager.create/prompt/cancel/entries/subscribe; он не
повторяет запуск процессов и авторизацию native Codex/Claude. Перед повторным
использованием проверяем, что create не копирует неявные пользовательские drafts,
MCP/skills и более широкие права. start/prompt/subscription не вызываются под
блокировкой дерева или SQLite.

## Пробелы хост-контракта, которые нельзя скрывать адаптером

Существующий create(NewAgentTask) не следует считать идемпотентным по нашему
operation ID. Нужна сохраняемая корреляция creation intent ↔ IDE task и возможность
найти уже созданную задачу после сбоя между create и записью связи. Если такого
поля/операции в хосте нет, расширяем контракт хоста с генерацией bindings, а не
повторяем create вслепую. Неопределённый исход уходит в reconciliation.

Просмотр внешней дочерней истории разрешает delegation ID через проверенную связь
в project/task ID. Нельзя передавать произвольный task ID из JSON модели прямо в
AgentManager.entries. Аналогично вопросы и разрешения маршрутизируются фактическому
исполнителю, а не текущему открытому диалогу.

Способность остановить внешний процесс не означает hard token budget или контроль
его собственных детей. Неизвестные расход/гарантии явно неизвестны; режим с жёстким
лимитом допускает только исполнителя, который способен его обеспечить.

## Очерёдность реализации и приёмка

1. Нейтральный протокол, repository и сервис: атомарные слоты, operation IDs,
   состояния, outbox, fake executor tests. Сразу оба варианта Target в контракте.
   Проверки: старый activation не закрывает повтор задания; старый consumer не
   подтверждает inbox; сбой между записью истории и ack не теряет/не дублирует
   итог; outcome не подменяет liveness; вопрос после смены activation отклоняется.
2. Внутренний Minerva executor и tool adapter: fresh ReadOnly ребёнок, выбранный
   route/effort, отдельная история, приветствие и доставка итога в родительский чат.
3. Адаптер OpenIDEA: discover реальных native engines, preflight прав, один
   управляемый ReadOnly запуск доступного движка. Проверка недоступного CLI,
   отсутствующей авторизации и unsupported control. Не сводим весь MVP к пункту 2.
4. Existing Subagent renderer и дерево/шапка: единая backend проекция, вопросы
   ребёнка, просмотр истории, сообщения и остановка с правильным адресатом.
5. Recovery/fallback: restart, повтор send/result, поздний итог старого activation,
   parent disconnect, shutdown во время старта, остановка внешних потомков.

Минимальный сквозной критерий: один родитель Minerva делегирует исследование
внутренней модели и установленному внешнему агенту; видны разные движки, отдельные
истории и итоги, а прав на запись им не добавлено. Тест на приветствие проверяет
доставку протокола, но не заменяет эту приёмку.
