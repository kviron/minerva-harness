# Экономия токенов и времени в цикле ReAct Minerva

Исследование от 27 ноября 2026 года. Основа для проектирования — рабочее дерево Minerva IDE на `2a725727b`, включая локальные изменения подготовки контекста. Область первой версии — агенты, чьими вызовами модели и инструментов управляет Minerva/Rig. Сюда входит подписка Codex как модель внутри Minerva. У самостоятельного Codex через app-server собственный цикл. [Границы исполнения](minerva-codex.md)

## С чего начать

Для профиля с 300+ инструментами я бы первой добавила настройку **«Загружать MCP-инструменты по запросу»**. Она влияет уже на первый запрос, в том числе для задач, которым MCP вообще не нужен. Второй независимый кандидат — компактный вывод тестов на последующих шагах.

### Первая версия для большого каталога MCP

На пользовательском снимке определения инструментов оценены в ~78 тыс. токенов, сообщения — в ~14 тыс., системная подсказка — в ~4,3 тыс. При этом общий счётчик показывает ~75,2 тыс. из 475 тыс. Категории приблизительны, а категория определений может включать встроенные инструменты. По снимку нельзя определить точный вклад MCP. В Minerva есть похожее различие: категории оцениваются локально, а итог при наличии данных берётся из usage провайдера. [Подсчёт схем запроса](../vendor/minerva/plugins/mh-providers/src/step_context.rs) · [Выбор источника итога](../vendor/minerva/plugins/mh-context/src/meter.rs)

1. **Использовать каталоги и переключатели OpenIDEA.** Для MCP брать действующий выбор серверов проекта и сессии, включая ограничения доверия. Список операций и точные схемы брать из активных регистраций этих серверов. Индекс для поиска строить по пересечению с допуском конкретного запуска. Отдельный список для ручной синхронизации не требуется. У MCP discovery Minerva есть предел 256 инструментов на один сервер, что следует учитывать для тестового каталога из 300+ инструментов. [Серверы сессии](../src/features/agents/mcpModel.ts) · [Отбор для запуска](../vendor/minerva/plugins/mh-agent-loop/src/conversation.rs) · [Адаптер Rig](../vendor/minerva/plugins/mh-tool-runtime/src/lib.rs) · [Обнаружение инструментов](../vendor/minerva/plugins/mh-mcp/src/lib.rs)
2. **На старте передавать базовые инструменты профиля и поиск по каталогу.** Например, агент разработки получает чтение, поиск по коду и нужные ему операции редактирования. При явном упоминании сервера или точного имени операции локальный поиск может сразу добавить подходящие схемы. Для поиска достаточно начать с имён, описаний, сервера и русско-английских синонимов. Качество поиска проверить на формулировках пользователя.
3. **Раскрывать несколько подходящих операций.** Для запроса «покажи последние запросы SQL-монитора» поиск по разрешённому каталогу подбирает инструменты статуса и чтения записей. Стартовая гипотеза — 3–5 схем с ограничением по их суммарному размеру. Модель затем вызывает операцию с её настоящей схемой. При промахе доступны повторный поиск, точное имя и просмотр операций конкретного сервера с постраничной выдачей. Загруженные схемы можно переиспользовать в пределах задачи. Проверять актуальность регистрации и права в момент вызова через существующий исполнитель.
4. **Учитывать возможности маршрута.** OpenAI документирует hosted и client-executed tool search, Anthropic — отложенную загрузку определений. Для совместимого маршрута проверить нативный протокол. На остальных поиск выполняет Minerva, а выбранные определения добавляются в следующий запрос. Такой путь может потребовать дополнительного обращения к модели и изменить кэшируемый префикс. [OpenAI Tool Search](https://developers.openai.com/api/docs/guides/tools-tool-search) · [Claude Tool Search](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)

**Как учитывать существующие переключатели.** Выключенный для сессии MCP-сервер исключается из поиска и исполнения, даже если его схема загружалась раньше. Включённый сервер доступен для поиска отдельных операций. Для skills используется действующий режим OpenIDEA: `auto` допускает автоматический выбор, `slashOnly` загружается по явной команде пользователя, `off` исключается. Для автоматического выбора достаточно имени и описания навыка до востребования его инструкции. У навыка и MCP-сервера разные настройки допуска: ссылка в тексте навыка сама по себе не включает сервер. Единственная новая опция профиля определяет момент загрузки; текущих переключателей достаточно для управления доступностью. [Режимы навыков](../src/features/agents/skillsModel.ts) · [Настройки текущей сессии](../src/features/agents/session/SessionComposer.tsx)

**Граница интеграции.** OpenIDEA формирует параметры сессии с `mcpServers`, отключёнными серверами и, для поддерживаемых драйверов, данными skills. В обработчиках создания и загрузки сессии встроенной Minerva я не нашла применения этих полей к каталогу Rig. Для пилота нужен сквозной тест через обычный чат: выбрать сервер, проверить доступные операции, выключить его и проверить выдачу поиска и прямой вызов ранее раскрытой операции. Аналогично проверить навык в режимах Auto, Slash и Off. [Передача параметров](../crates/ide-agent/src/lib.rs) · [Обработчики Minerva](../crates/ide-agent/src/native/minerva.rs)

**Первый эксперимент.** Сравнить полный набор с загрузкой по запросу на одном снимке допущенных регистраций, одной модели и одном effort. Использовать четыре вида задач: без MCP, с одним частым инструментом, с редким инструментом по русскому описанию, с цепочкой из двух серверов. На первом шаге зафиксировать размер фактически объявленных схем с разбивкой по серверам и общие входные токены провайдера. На всей задаче измерять долю успешных решений, число поисков, попадание нужной операции в первые пять, токены с учётом кэша, время до первого полезного вызова и до проверенного результата. Так станет видно, когда меньший первый запрос окупает дополнительный шаг поиска.

### Следующая гипотеза для длинных логов

Агенту обычно нужны исход команды, конкретная диагностика и возможность прочитать детали. Передача сотен успешных проверок расходует входное окно при первом чтении лога и при каждом последующем шаге, на котором лог ещё присутствует в истории. Если при сокращении теряется сама диагностика, агенту может понадобиться ещё один раунд поиска или повторный запуск.

### Что обнаружилось в Minerva

- При подготовке запроса к модели функция `prune_text` сокращает результат длиннее 8192 байт. Она оставляет первые 4096 и последние 2048 байт вместе с отметкой о сокращении. Это уже часть базового поведения. [Подготовка сообщения](../vendor/minerva/plugins/mh-providers/src/lib.rs) · [Реализация сокращения](../vendor/minerva/plugins/mh-context/src/lib.rs)
- При включённом автоматическом сжатии есть ещё один порог, обычно 80% окна, с поправкой на лимиты маршрута. Сначала сокращается старый вывод инструментов. Если этого мало, модель может составить сводку завершённых обменов. Сравнивать новую фичу следует с этими механизмами в их обычной конфигурации. [Проекция каждого шага](../vendor/minerva/plugins/mh-providers/src/step_context.rs) · [Сводка завершённых обменов](../vendor/minerva/plugins/mh-providers/src/step_compaction.rs)
- Счётчик контекста обновляет одну запись на сессию. Он подходит для отображения размера текущего запроса. Для сравнения вариантов нужна сумма по всем шагам, включая неудачные попытки, служебные сводки и дочерних агентов. [Счётчик запроса](../vendor/minerva/plugins/mh-context/src/meter.rs)

**Локальная проверка.** Я скомпилировала текущую Rust-функцию `prune_text` и передала ей синтетический лог из 500 тестов. В каждом прогоне один тест имел статус `FAILED` и строку `src/parser.rs:42: assertion left 7 right 8`. Исходный лог занимал 10 548 байт, после сокращения оставалось 6 225. Для тестов № 1 и 500 диагностика сохранилась, для № 251 — исчезла. Проверка изолирует поведение функции. Частота таких случаев в пользовательских сессиях и влияние на время выполнения требуют замера на полном цикле.

## Контракт для эксперимента с компактным выводом тестов

1. Профиль агента может включить режим компактных результатов. При старте выполнения Minerva фиксирует его значение в параметрах запуска, чтобы повтор и сравнение использовали известную политику.
2. Для одного поддержанного формата тестов рантайм один раз готовит представление для модели. Оно содержит код выхода, число прошедших, упавших и пропущенных тестов, имена упавших тестов, первичную диагностику с путём и строкой, если они доступны. Отдельные состояния нужны для таймаута, отмены, ошибки запуска и неполного вывода. Неизвестные счётчики остаются неизвестными.
3. Модель получает признак сокращения и ссылку на сохранённый результат в пределах сессии. По ссылке можно прочитать диапазон или найти строку без повторного запуска команды. Для источника с кольцевым буфером требуется сохранить нужный вывод до вытеснения либо явно сообщить, какая часть потеряна. Если парсер не распознал формат, используется обычный вывод с его действующими ограничениями.
4. Последующие шаги используют то же представление и тот же идентификатор вызова. Журнал сохраняет доступное исходное наблюдение. Обычные проверки доступа применяются и при чтении подробностей. Для длинных сессий действуют существующие механизмы сжатия.

## Отдельный эксперимент для вывода тестов

**Сначала — дешёвая проверка на сохранённых результатах.** Взять логи реальных тестов и примеры с ошибкой в начале, середине и конце, несколькими независимыми падениями, обрывом и неизвестным форматом. Сравнить действующий и компактный вывод по размеру, сохранности первичной диагностики и возможности открыть детали. Это проверяет представление данных. Из такого повтора нельзя вывести, сколько шагов сделает агент.

**Затем — парный пилот на полной задаче.** Стартовый дизайн — 24 задачи, по шесть на локализацию, локальное исправление с тестом, многофайловую правку и диагностику шумного прогона. Для каждого варианта по три независимых запуска на задачу. Зафиксировать ревизию проекта, версии модели и тестов, effort и бюджет, сбрасывать состояние проекта между попытками, перемешивать порядок A/B. Холодные и прогретые запуски учитывать раздельно. A — текущая Minerva, B — та же конфигурация с компактным выводом тестов. Числа задают размер пилота. Для вывода о малых различиях в качестве может потребоваться больше задач. | Что измерять                  | Как считать                                                                                                                                                                                                                     |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Качество                      | Доля задач, принятых с первой попытки по независимым проверкам. Для локализации проверять файл и причину, для изменения — целевые и регрессионные тесты. Отдельно разобрать пары, где прошёл только один вариант.               |
| Токены на принятую задачу     | Сумма входных и выходных токенов всех попыток, делённая на число принятых. Сверить правила провайдера и выделить cache read/write и reasoning без двойного счёта. Отсутствующие данные помечать.                                |
| Время пользователя            | От старта до проверенного результата. Показать медиану и p95, таймауты и незавершённые задачи. Разложить трассу на модель, инструменты, запуск процессов и ожидание. Для параллельных операций учитывать перекрытие интервалов. |
| Стоимость и причина изменения | Стоимость всех попыток на принятую задачу при известных тарифах. Для подписки показывать доступный usage. Также считать вызовы модели, повторные команды, чтения полного лога, сжатия и долю кэшированного входа.               |

Я бы принимала решение по парным разницам с интервалами неопределённости по задачам. До пилота стоит зафиксировать допустимую потерю качества и минимально полезный выигрыш. Для режима с целью экономить и токены, и время нужны улучшения обеих величин при приемлемом качестве. Если выигрывает только один класс задач, это основание предложить настройку соответствующему профилю. Локальная проверка выше подтверждает потерю строки при обрезке. Величину выигрыша полного агента даст A/B.
