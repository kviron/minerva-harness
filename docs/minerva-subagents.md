## Как включить делегирование

Закройте OpenIDEA и задайте `services.delegation.enabled` равным `true` в
`minerva/minerva.conf.json` каталога конфигурации нужной сборки. Сохраните
остальные настройки файла. На Windows стандартный каталог конфигурации
находится в `%APPDATA%\<идентификатор сборки>`. Если задана переменная
`OPENIDEA_CONFIG_DIR`, сборка использует одноимённый подкаталог в ней.

После запуска откройте чат Minerva в нужном проекте и попросите агента
поручить субагенту отдельную задачу. Список поручений открывается кнопкой
«Субагенты» справа от заголовка чата. Установленные Codex и Claude Code
используются через собственные подключения OpenIDEA.

На Windows новое поручение может получить ограниченную запись файлов, если
её разрешает политика родительского чата. При запросе подтверждения карточка
указывает исполнителя и файл. Разрешение действует для одного вызова.
Minerva может выдать новый допуск через `subagent_send` с `writable: true`
после успешного завершения предыдущего поручения и при пустой очереди.
Для Codex исходный диалог должен быть создан с файловыми инструментами
OpenIDEA. Обычные сообщения в очереди выполняются в режиме чтения.

`services.delegation.executionDeadlineSeconds` задаёт срок выполнения одного
поручения. По умолчанию это 900 секунд, значение `0` отключает автоостановку.
После истечения срока Minerva запрашивает остановку. Поручение занимает слот
до подтверждения завершения.

## Владение и минимальный протокол

- Каждый ребёнок — обычная Minerva-сессия с session ID, root session ID, parent session ID, именем и задачей. Один существующий runtime и один общий механизм хода Rig обслуживают дерево. Связи хранятся в SQLite. Состояние ребёнка различает выполнение, ожидание ввода, простой и конечный исход конкретного запуска. Завершённый запуск допускает последующее продолжение того же диалога с новым activation ID.
- Предлагаемые операции протокола — start, send, wait, interrupt, list. Для каждого запроса задаём ID операции. send содержит message ID, sender session ID и target session ID; backend устанавливает отправителя из контекста исполнения. Имя служит отображению, адресация использует ID. Получатель подтверждает сохранение, позднее отдельно фиксирует приём сообщением в конкретный ход. Повтор доставки не создаёт второй экземпляр.
- Родитель задаёт понятную задачу, ожидаемый результат и материалы. В первой реализации используем fresh-контекст с явно переданными материалами и инструкциями проекта. У ребёнка собственный бюджет и сводки. Позднее fork получает зафиксированный совместимый префикс истории, с описанием того, какие незавершённые части в него входят.
- Маршрут и effort задаются при запуске ребёнка в пределах допущенных хостом маршрутов. При отсутствии выбора используем эффективный маршрут родителя на момент запуска. Последующие переключения родителя не меняют ребёнка. Смена модели выбранного ребёнка идёт через общий механизм pending selection и применяется на его границе шага.
- Сообщения parent → child, child → parent и между детьми одного дерева используют общий inbox. Работающий адресат получает уточнение, простаивающий — новый ход. Управляющая операция возобновления отдельно проходит проверку актуальных прав. После явной пользовательской остановки автоматическое пробуждение блокируется до разрешённого продолжения. Сообщение модели не расширяет полномочия получателя.
- Итог ребёнка сохраняется в его истории. Уведомление менеджера содержит activation ID, статус и ссылку на итог, доставляется непосредственному родителю один раз с восстановлением после временного отключения UI или родителя. Полный журнал ребёнка доступен для просмотра, в контекст родителя входит ограниченный итог. Ошибка доставки сохраняется как pending. Это наше требование надёжности, в изученном DSH доставка результата ограничена онлайн-создателем.
- wait подписывается на события выбранных activation ID и завершается по изменению, результату, отмене или ограниченному ожиданию. Ожидание не удерживает блокировку хранилища и не мешает приёму сообщений. Простое ожидание ответа родителя не запускает бесконечные модельные запросы. Счётчик активных запусков учитывает starting и stopping. Число запросов, доступные слоты и бюджет ограничиваются всем деревом.
- Стартовые параметры MVP предлагаются как глубина один и до трёх одновременно работающих детей. Ёмкость резервируется атомарно. На первом этапе дети выполняют исследовательские задачи в ReadOnly. Запись несколькими агентами требует отдельного решения по сериализации изменений либо изолированным worktree и включается после его проверки. Права ребёнка ограничены текущими правилами проекта и выданным ему набором инструментов. Запрос разрешения явно указывает ребёнка и его cwd.
- Остановка одного ребёнка отменяет его активный запуск. Операция «Остановить всех» адресуется дереву. Обычный Stop родительского хода сохраняет детей работающими, интерфейс продолжает показывать их активность. Закрытие представления чата сохраняет выполнение. Shutdown приложения отменяет всё дерево и дожидается освобождения ресурсов. После рестарта незавершённые запуски показывают прерванный статус, просмотр и явное продолжение доступны по прежним ID.

## Навигация OpenIDEA

В списке истории основной чат имеет раскрывающую стрелку. Под ним показываются дочерние диалоги с именем, задачей и статусом; активные и ожидающие ответа заметны сразу, завершённые остаются доступны после перезапуска. Раскрытие списка сохраняется независимо от выполнения.

В шапке разговора находится переключатель «Основной / Субагенты» со статусами. Выбор ребёнка открывает его сообщения в рабочей области этого диалога. Возврат к родителю доступен из той же шапки. Черновики, scroll, выбранная модель и адресат ввода изолированы по session ID. Composer явно показывает адресата. Открытие дочерней истории не переадресует уже ожидающий ответ в диалоге разрешения. При новом вопросе ребёнка обе точки навигации показывают ожидание ввода.

В OpenIDEA уже есть AgentEntry::Subagent, AgentSubagentStatus, события с subagent ID, entriesKey(task, subagent) и оформление дочерних разговоров. Сначала проверяем их полноценное переиспользование после upstream update. Источником состояния служит backend дерева; список истории и шапка читают одну проекцию. Новые элементы используют существующие кнопки, дерево, меню и токены. Перед завершением UI-изменения обязательны независимая визуальная проверка и проверка в работающем приложении.

## Карта кода и приёмка

Актуальная граница внутреннего tool-плагина, общего delegation service и двух executor adapters определена в [решении от 26 ноября](minerva-delegation-design.md). Оно заменяет раннее предложение складывать lifecycle и доставку в subagents.rs внутри mh-agent-loop. Нейтральный протокол принадлежит SDK, SQL — mh-sessions, установка executor ports — composition root runtime; OpenIDEA сохраняет владение внешними процессами и их историей.

Проверяем запуск двух детей и ранний отказ при исчерпании слотов, прямое сообщение между детьми, повтор send, результат после отключения родителя, вопрос ребёнка при открытом родительском чате, неверный адресат и чужое дерево. После создания ребёнка меняем модель родителя и убеждаемся в независимости маршрутов. Открываем дочерний диалог из дерева и шапки, отправляем уточнение, возвращаемся к сохранённому черновику родителя. Проверяем индивидуальную остановку, Stop родителя, Stop All, рестарт и единственность доставки результата. Отдельно проверяем отказ записи ребёнку и атомарный лимит при одновременном старте.

Оркестрация native-движков следует следующим срезом расширенного MVP и описана ниже. Fork истории, вложенное делегирование и общая DAG-доска задач отложены.

## Оркестрация движков OpenIDEA и выбор исполнителя

Уточнение пользователя расширяет делегирование исполнителями Claude Code, Codex и другими доступными движками OpenIDEA. Minerva может назначить задачу другой API-модели своего Rig runtime, включая DeepSeek Flash, либо движку со своим циклом. Выбор включает engine, provider/model и effort, если исполнитель поддерживает эти настройки. Фактические ID и допустимые значения получаем из текущего каталога. Названия Terra/Astra служат пользовательскими примерами предпочтений.

OpenIDEA уже предоставляет create(NewAgentTask), prompt, send_queued_now и cancel, а native-адаптеры публикуют capabilities через initialize. Codex shim поддерживает steer с expectedTurnId, Claude shim также объявляет steer. Используем эти сервисы через типизированный host-контракт. Доступность каждого свойства подтверждаем установленным движком и его версией. [Адаптеры OpenIDEA](../crates/ide-agent/src/native/mod.rs) · [Сервис задач](../crates/ide-agent/src/lib.rs)

### Граница исполнения

Решение пользователя — переиспользовать готовые механизмы. Перед изменением каждого контракта проверяем его через существующий сервис и штатную точку входа. OpenIDEA AgentService уже предоставляет create, prompt, send_queued_now, cancel и ответы на запросы пользователя; адаптеры публикуют capabilities. Их семантика служит основой host-моста. Операции Minerva делегируют в эти сервисы после проверки принадлежности дереву и полномочий. Существующие AgentEntry::Subagent, entriesKey и renderer обслуживают отображение. Runs, session_store и credential store сохраняют свои обязанности. Новый код добавляем для отсутствующих связей дерева, политики назначения и доставки результатов. Для каждого предлагаемого нового компонента в задаче реализации указываем проверенный пробел существующего API. После обновления upstream повторно проверяем эти пробелы.

Minerva владеет планом делегирования, связями parent/child, выбором разрешённого исполнителя и получением результата. Прямой API-ребёнок исполняется существующим runtime Rig. Для Claude Code/Codex OpenIDEA владеет native-процессом, авторизацией, протоколом, нативной сессией, разрешениями и событиями. Сжатие и wire-history такого ребёнка остаются у движка. Связь хранит orchestration child ID, activation ID, IDE task ID, engine session ID и cursor наблюдения. Авторитетную историю пишет её исполнитель, Minerva хранит ссылки и ограниченный результат.

В plugin-sdk предлагаем DelegationBackend с describe, start, observe, send и interrupt. Операции объявляют поддержку resume, steer, model/effort selection и вывода diff. Типы контракта не зависят от ide-agent. Реализация host-моста располагается в ide-agent и передаётся при сборке через ide-minerva; это предотвращает обратную зависимость vendor runtime от IDE. Долгое выполнение наблюдается вне блокировок координатора. Если текущая сборка не допускает такой инъекции, первым прототипом уточняем точку wiring. Дочернюю задачу учитываем в существующем task store, дерево отображаем через единую проекцию связей. Диалог CLI открывается существующим renderer его адаптера.

DSH также отделяет локальных continuable детей от внешних запусков: в изученном контракте внешние backend не принимают follow-up. Для Minerva поведение внешнего движка определяется фактическими возможностями адаптера OpenIDEA. Отсутствие steer означает сохранение сообщения для следующего допустимого хода либо явный отказ операции. [Backend-контракт DSH](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/docs/subsystems/subagent.md)

### Политика назначения и замены исполнителя

Пользователь задаёт допущенные engine/model routes и предпочтения. Оркестратор получает каталог разрешённых кандидатов с возможностями, пределом контекста, допустимыми efforts и известным состоянием доступности. Простая ограниченная задача может идти быстрой модели с низким effort; неоднозначная задача с несколькими зависимостями — более сильной с повышенным effort. Для каждого назначения сохраняем краткое основание выбора. Достоверные цены используем только при наличии проверенных данных; условная группа стоимости не подменяет фактические расходы.

Критерии выбора включают требуемые инструменты, формат входа, язык/тип задачи, бюджет, разрешения и необходимость изменения файлов. Конкретные модели Terra/Astra, DeepSeek Flash и Claude Code доступны только при наличии соответствующих подключений. Перед запуском проверяем установку движка, авторизацию в пределах поддерживаемого probe и capabilities. Каталог и успешный probe не гарантируют следующий ответ API. Проверку результата задаём вместе с задачей: например, перечень найденных мест с источниками или прохождение конкретной команды. Неуспешная проверка может разрешить одну эскалацию по заранее выбранной цепочке и общему лимиту попыток. Другая модель продолжает с кратким заданием и подтверждёнными результатами предыдущей попытки.

При недоступности кандидата выбираем следующего из допущенных, способного выполнить задачу с теми же ограничениями. Повтор запрещён для неподходящего кандидата и после исчерпания общей цепочки. Ошибка до запуска допускает немедленную замену. Для rate limit учитываем retry-after и пользовательский бюджет ожидания. Ошибки входных данных и запрет политики сначала возвращаем координатору, смена модели сама по себе их не исправляет. Разрыв после возможной записи требует выяснения состояния workspace и подтверждения остановки прежнего исполнителя до запуска замены. Двойное исполнение изменяющей операции исключаем на уровне activation и версии ресурса. Если проверить исход нельзя, показываем блокирующее состояние с сохранёнными данными.

В чате фиксируем назначение, недоступность и замену, например «DeepSeek Flash недоступен; задача передана Claude Code». Пользователь может закрепить исполнителя: для такого назначения разрешение на fallback задаётся отдельно. При отсутствии подходящих кандидатов сохраняем задачу и показываем причину. У ребёнка в шапке и дереве видны фактический движок, модель и статус. Effort показывается только при поддержке.

### Граничные условия для первого прототипа

Это проектные требования Minerva, полученные при проверке согласованности плана.

- **Взаимное ожидание.** Родитель может ждать ребёнка, пока ребёнок ждёт ответа родителя. wait завершается также при потребности в сообщении или пользовательском вводе. Явные зависимости ожиданий проверяем на цикл. Отсутствие новых событий само по себе не создаёт модельный запрос. Проверка: A ждёт B, B задаёт вопрос A; координатор сообщает потребность во вводе и допускает ответ.
- **Устаревший результат.** activation связываем с версией задания и исходной версией workspace. После изменения задания, смены ветки либо правки файла результат прежнего запуска сохраняет эту привязку. Оркестратор проверяет актуальность перед применением рекомендации. Завершение отменённого запуска не завершает его замену и не применяется автоматически.
- **Приоритет пользовательской команды.** Прямое уточнение ребёнку отмечает источник user и адресата. Родитель видит факт изменения задания. Пользовательский Stop блокирует автоматический restart от запоздалого уведомления либо очередного сообщения родителя. Разрешение пользователя связано с конкретной операцией ребёнка.
- **Способности и вложенное делегирование внешнего CLI.** Ограничения дерева должны учитывать детей, создаваемых самим Claude Code/Codex. В первом прототипе проверяем возможность отключить такое делегирование либо учесть его в лимитах и остановке. Если нужную гарантию адаптер не обеспечивает, она явно отражается в доступности кандидата для задачи. Проверяем на установленной версии CLI, включая фактические инструменты и разрешения. Native auth, middleware и shared subscription rate limit могут отличаться от прямого API.
- **Результат и проверка.** Статус done означает завершение исполнения. Критерий задачи проверяется отдельно. Результат хранит статус проверки и ссылки на полученные доказательства, например exit status команды. Смена модели после неверного ответа ограничена общим бюджетом и не сбрасывает его. Ошибку проверки отличаем от ошибки выполнения самой проверяющей команды.
- **Жизненный цикл дерева.** Архивирование сохраняет историю и останавливается на согласованном поведении активной задачи OpenIDEA. Удаление родителя с активными детьми сначала требует завершить дерево через штатный guarded-процесс. Ресурсы детей и ссылки на результаты удаляются с учётом оставшихся ссылок. Запрет доступа к удалённому проекту применяется до следующего действия, смена выбранного проекта в UI не переопределяет cwd уже запущенного ребёнка.

### Сверка с практикой других оркестраторов

Проверка первичных источников выполнена 24 ноября 2026 года. Приведённые ниже решения Minerva являются адаптацией механизмов к существующему runtime и хосту.

OpenAI Agents SDK описывает manager pattern: основной агент вызывает специалистов как инструменты и сохраняет ответственность за разговор. Структурированный выбор категории позволяет коду проверить назначение. Для Minerva LLM предлагает кандидата и задачу, а код проверяет доступность, разрешения, лимиты и выполняет переход. Предложение не меняет состояние сессии до принятия координатором. Хостовые проверки не передаём модели-оркестратору. [Оркестрация Agents SDK](https://openai.github.io/openai-agents-python/multi_agent/)

Claude Code Agent Teams предоставляет ведущего, адресные сообщения и захват задач под блокировкой. Его документация отдельно описывает невозможность подтвердить пользовательское разрешение сообщением другого агента, задержки shutdown и ограничения resume. Для Minerva это основания проверять квитанцию сохранения, актуального владельца и происхождение сообщений, а также различать остановку и подтверждение освобождения ресурсов. [Agent Teams](https://code.claude.com/docs/en/agent-teams)

AutoGen различает остановку по условию и принудительную отмену, позволяет возобновлять команду после окончания запуска. В Minerva отдельны запрос остановки, прекращение приёма новой работы и подтверждённое завершение activation. Ожидание наблюдает события и не занимает слот модельного запроса. [Teams AutoGen](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/teams.html)

Политика проекта действует независимо от предложенного исполнителя. Назначение более привилегированному агенту требует действующего пользовательского допуска к конкретной операции.

### Приёмка внешнего исполнителя

После локальных ReadOnly-детей проверяем одну задачу исследования через API-модель и одну через реально установленный native-движок. Родитель видит запуск, текущую активность, запрос ввода и итог; пользователь открывает полную историю из дерева и шапки. Проверяем недоступный CLI, истёкшую авторизацию, отсутствие модели, rate limit, замену до старта и исчерпание цепочки. Отдельные проверки охватывают отсутствие steer, рестарт IDE с внешней сессией, независимую отмену и ошибку сохранения связей. Тест подменяет исполнителя после потери ответа о записи и доказывает отсутствие второй записи.

Общие бюджеты дерева включают все движки; когда CLI не сообщает точные токены, показываем неполноту измерения и применяем доступные ограничения по числу запусков и времени. Запись native-ребёнком в MVP разрешается только после подтверждения эквивалентных ограничений доступа и согласованного режима работы с файлами. Исследовательский первый срез проверяет принудительный ReadOnly установленного движка. Вариант, неспособный обеспечить требуемые ограничения, исключается из кандидатов для этой задачи.
