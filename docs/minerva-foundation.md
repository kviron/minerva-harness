# Minerva на основе OpenIDEA: план перехода

Актуальные границы встроенного агента и порядок работ на 24 ноября 2026 года описаны в [плане MVP](minerva-agent-mvp.md). Он пересматривает прежнее требование о поддержке MH-плагинов в IDE. Ниже сохранён исходный план перехода.

Дата: 2026-11-20. Исходный план; первая интеграция реализована в отдельном
репозитории `C:\dev\minerva-ide`. Фактическое устройство и проверенные ограничения
описаны в [minerva-integration.md](minerva-integration.md).

## Решение

Для цели «максимально близкая к OpenIDEA полноценная IDE с агентным слоем
Minerva» предпочтительна основа OpenIDEA, а не перенос всей IDE в оболочку
Minerva. Рекомендация условна до проверки интеграции и продуктовых требований
этапов 0–2. Текущий Minerva сохраняется как рабочая система и источник
агентного runtime; переход не начинается с удаления или переписывания проекта.

Исходный запрос: проводник по предоставленному скриншоту, редактор, LSP и
сопутствующие функции максимально близко к OpenIDEA; затем расширение цели
до всей программы и её дизайн-системы.

Уточнение пользователя: Minerva не подключается как внешний ACP-агент.
Наш агентный слой встроен в приложение; он поддерживает прямые модельные API,
а также Claude Code и Codex через драйверы исполнения, как в OpenIDEA.

Последующее уточнение: сохранить режим обычного чата и режим «Разработка».
В «Разработке» показывается полноценный workbench OpenIDEA, агентный чат —
сбоку. Основой чата и управления задачами становится их реализация; наш
отдельный экран не переписывается заново. Поддержка существующих плагинов
Minerva обязательна. Эти решения уточняют формулировки этапов ниже.

## Компоновка и повторное использование

- Обычный режим: разговор с агентом как основная рабочая область.
- «Разработка»: Project слева, редактор/вкладки в центре, агентный чат справа,
  штатные инструментальные окна IDE в предусмотренных workbench областях.
- Переключение режима меняет компоновку, сохраняя выбранную задачу, поток
  ответа, draft, ожидаемые вопросы/разрешения и состояние открытых документов.
- Переиспользовать Agents UI, renderer событий, task navigation и настройки
  OpenIDEA. Добавлять только отсутствующие Minerva-возможности.
- Для обычного режима проверить возможность размещения того же chat surface
  как основной области. Не поддерживать два независимых renderer и store чата.
- Их менеджер задач и история представления — исходная основа; Minerva
  сохраняет только необходимые ему execution/replay данные. На этапе прототипа
  выбрать единственного владельца каждого состояния и отображаемой истории.
  Не переносить целиком наш session manager поверх существующего task manager.

## Обязательная совместимость плагинов Minerva

1. Инвентаризировать реально установленные пакеты: manifest, backend protocol,
   сервисы/зависимости, UI entry, используемые слоты, секреты и данные.
2. Сохранить Minerva plugin host и его работающие контракты там, где нужны
   наши пакеты. OpenIDEA plugin system продолжает обслуживать свои плагины;
   бинарную совместимость этих систем не предполагать.
3. Встроить lifecycle Minerva host в IDE backend. Обеспечить включение,
   отключение, падение и отзыв сервисов без перезапуска IDE; не запускать
   вторую копию одинаковых MCP/tool services ради каждой системы плагинов.
4. Сопоставить UI-слоты Minerva с contributions OpenIDEA. Проверить существующие
   bundles и imports SDK: перенос дизайна оболочки не должен молча ломать
   уже выпущенные UI-плагины. При необходимости сохранить совместимый набор
   экспортов SDK, а собственные экраны постепенно оформить средствами IDE.
5. Доступ из прямого Minerva loop к plugin tools сохранить. Для Claude/Codex
   отдельно проверить поддерживаемый способ экспозиции нужных tools, например
   через существующий MCP-механизм; подключение инструментов не означает
   автоматический перенос всей семантики Minerva plugins в native engine.
6. Провести проверку на review-example и реальном пользовательском пакете:
   установка, UI, service calls, tool call, disable/re-enable, crash и restart.
   Сохранить правила доверия и не выдавать новый доступ при миграции.

Это отдельный обязательный этап после первого встроенного API-прототипа
и до миграции данных/выпуска. Его нельзя заменить переносом одного чата.

## Проверенная основа

Изученный upstream: `l0ng-ai/openidea`, коммит
`8c696b8fe7cb05922d312c8ca40fe9ecd6aef30b`.

- `src/features/project-tree/`: проводник, файловые операции, меню и модель дерева.
- `src/ui/Tree.tsx`: общий компонент дерева.
- `src/editor/core/`: CodeMirror 6, документы, вкладки, синхронизация с Rust.
- `src/editor/lsp/`: completion, диагностика, hover, navigation, rename,
  formatting, intentions, inlay hints и другие расширения.
- `crates/ide-lsp`: LSP backend с собственными зависимостями IDE.
- `src/features/agents/`: агентное окно, задачи и редактор разговоров.
- `crates/ide-agent/`: ACP, native-драйверы, история и worktree.
- `crates/ide-agent/src/provider.rs`: пользовательские ACP-провайдеры;
  DeepSeek Harness уже указан среди встроенных провайдеров.
- `docs/en/contribute/architecture/boundaries.mdx`: Rust владеет I/O,
  документами и исполнением; frontend — представлением и взаимодействием.

Это доказательства по исходникам, а не проверка работоспособности сборки.

В Minerva уже существуют агентный runtime, durable history, инструменты,
взаимодействия, MCP, навыки, контекст и плагины. Собственный редактор находится
в `apps/web/src/plugins/editor/`; файловый backend — `plugins/mh-editor`,
LSP — `plugins/mh-lsp`. Последний сейчас принимает completion, hover,
definition и references, а frontend получает диагностику опросом.
Minerva имеет собственные HTTP/Tauri/gateway-контракты и ограничения hosted.

## Варианты

| Основа                                      | Что переносим                                                  | Последствия                                                                                                    |
| ------------------------------------------- | -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Текущая Minerva                             | Проводник, CodeMirror, LSP, затем остальные части IDE          | Сохраняет оболочку, но требует адаптировать много взаимосвязанных подсистем и постоянно переносить исправления |
| OpenIDEA + встроенный агентный слой Minerva | Rust-сервисы харнеса, свой агентный экран и интеграция движков | Сохраняет IDE целиком; основной объём работы сосредоточен на агентной системе                                  |
| Глубокое слияние двух приложений            | Два runtime, plugin host и оболочки                            | Наибольшая связанность; не выбирать исходным решением                                                          |

Предпочтителен второй вариант. Minerva интегрируется напрямую на уровне
Rust-сервисов и типизированных команд IDE, без внешнего ACP-моста.

## Целевая архитектура

```text
OpenIDEA fork
  workbench + дизайн-система + настройки + редактор + проводник + LSP
  агентный экран Minerva на UI-примитивах и contributions OpenIDEA
                    |
         встроенный Minerva Agent Service (Rust)
         sessions + history + permissions + context + skills + plugins
                    |
         +----------+------------------+
         |          |                  |
    Minerva loop  Claude Code        Codex
    model APIs    native driver      app-server driver
    + tools/MCP   upstream           upstream
```

IDE владеет проектом, открытыми документами и пользовательским редактором.
Minerva владеет запуском агента, его историей, вызовами инструментов,
разрешениями и состояниями ожидания. Точный способ передачи контекста
несохранённых документов и применения изменений устанавливается в этапе 2.

Модель и движок исполнения — разные сущности. В режиме прямого API циклом
модель → инструменты → модель управляет Minerva. В режиме Claude Code/Codex
цикл выполняет соответствующий движок; Minerva управляет задачей и отображает
его события, без второго агентного цикла поверх первого. Возможности зависят
от движка: не обещать одинаковые tools, compaction, MCP и permissions там,
где драйвер этого не предоставляет. Изучить внутреннюю ACP-нормализацию
upstream-драйверов; её наличие не требует запускать Minerva как ACP-процесс.

Не переносить Cordis и старую оболочку во все подсистемы OpenIDEA.
Cordis остаётся внутренней архитектурой Minerva. Не переписывать upstream
дизайн-систему под shadcn или assistant-ui. Требуемые Minerva-экраны оформлять
через UI-примитивы и contributions OpenIDEA.

## Этап 0. Зафиксировать границы продукта

1. Составить таблицу всех функций Minerva: оставить runtime, использовать
   эквивалент IDE, перенести UI или отложить с явным указанием потери.
2. Отдельно описать desktop, browser, remote backend и hosted/multi-user.
   Не считать remote OpenIDEA эквивалентом браузерной Minerva с изоляцией
   пользователей. Исследовать transport, auth, storage и процессную изоляцию.
3. Инвентаризировать историю, вложения, секреты, плагины, настройки моделей,
   разрешения, compaction, память и навыки; отметить обязательные сценарии.
4. Определить границу встроенного Agent Service, frontend feature и
   расширений. Не предполагать совместимость plugin SDK двух систем.

Готово: согласованная таблица сохранения функций; браузерные требования
не исчезли незаметно. Если browser/hosted блокирует основу OpenIDEA,
решение пересматривается до массового переноса.

## Этап 1. Воспроизводимая исходная IDE

1. Подготовить отдельный checkout/fork на указанном upstream-коммите.
2. Собрать и запустить исходную IDE на Windows; записать версии инструментов,
   зависимости, команды и реальные сбои. Не исправлять их через старую Minerva.
3. Проверить проект, проводник, сохранение, поиск, Git, терминал и LSP на
   тестовом репозитории; записать исходные скриншоты и поведение.
4. Проверить LICENSE, NOTICE, сторонние ассеты и ограничения дистрибуции;
   сохранять upstream-уведомления при заимствовании и ребрендинге.
5. Настроить upstream remote и небольшой отдельный набор наших изменений;
   не смешивать импорт с массовым форматированием и переименованием файлов.

Готово: рабочая базовая сборка и воспроизводимые проверки до интеграции.

## Этап 2. Встроенный Agent Service и первый прямой модельный API

1. Выделить существующие сервисы Minerva из композиции старого приложения:
   сначала проверить зависимости runtime от Harness, хранилища и plugin host.
   Подключить их Rust-крейтами к IDE backend, без второго сервера/оболочки.
2. Добавить типизированные команды и события Agent Service через ide-host;
   Tauri остаётся транспортом. Не копировать старый HTTP API в каждый экран.
3. Встроить первую вертикаль нашего экрана в штатную вкладку редактора:
   сессия, выбранная модель, streaming, tool calls/results, cancel, permissions.
   Использовать существующий Minerva loop и один прямой API-провайдер.
4. Установить единый контракт событий: вопросы, изображения, reasoning,
   ошибки, usage, compaction, ветвление, версии состояния и reconnect.
   История остаётся пригодной для replay и не зависит от компонентов UI.
5. Проверить файловые инструменты: единый владелец изменения, dirty buffers,
   внешний diff, версионирование, конфликт агентной записи с редактором.
   Учесть разницу cwd проекта, worktree задачи и workspace Minerva.
6. Разрешение должно иметь одного владельца. Исключить двойные prompts,
   обход Minerva policy и автоматический повтор действий после reconnect.
7. Проверить завершение IDE, падение runtime и отмену subprocess tree;
   определить поведение работающей задачи при закрытии её вкладки.

Готово: разговор → инструмент → разрешение → изменение файла → отображение
изменения в IDE → продолжение; cancel, reload и resume без двойного исполнения.
Сначала детерминированный fixture, затем один реальный провайдер.

После этого этапа принять окончательное решение об основе. Критерий —
не наличие вкладки чата, а сохранение обязательных сценариев Minerva.

## Этап 2б. Claude Code и Codex как движки нашего агентного слоя

1. Исследовать зависимости native-драйверов в `crates/ide-agent/src/native/`:
   запуск, авторизация, stream translation, approvals, load/resume и отмена.
   Переиспользовать рабочий upstream-код через минимальную границу сервиса.
2. Ввести только реально нужные операции движка: start/resume, send, cancel,
   ответ на взаимодействие, поток событий и capabilities. Не строить новый
   универсальный SDK для предполагаемых будущих движков.
3. Добавить в наш экран выбор движка: Minerva API / Claude Code / Codex.
   В прямом режиме отдельно выбирается модель/провайдер; в native-режимах
   показываются модели, настройки и вход, поддерживаемые этим движком.
4. Согласовать владельцев истории, разрешений, MCP, навыков и контекста для
   каждого режима. Родная история движка может быть нужна для resume;
   её session ID хранится с задачей, она не заменяет историю отображения.
5. Проверить каждый движок отдельно: login failure, tool approval, stop,
   restart, resume и недоступная возможность. Не переносить управление
   их инструментами в Minerva без поддержки соответствующего протокола.

Готово: единый наш агентный экран работает с тремя маршрутами исполнения,
сохраняя различия capabilities и не запуская вложенные агентные циклы.

## Этап 3. Полный агентный экран в дизайне OpenIDEA

1. Сохранить штатные tool windows, вкладки задач и навигацию OpenIDEA.
2. Подключить Minerva models/providers, навыки, MCP, память и контекст.
   Использовать существующие IDE-настройки, где семантика совпадает.
3. Для отсутствующих возможностей добавить локальные features/contributions:
   настройки Minerva plugins, usage/compaction, вопросы, approval и артефакты.
4. Привязать selection/files/diagnostics к контексту агента, а результаты —
   к открытию файла, диапазона и diff через штатные сервисы редактора.
5. После покрытия сценариев наш экран становится основным агентным интерфейсом.
   Штатный Agents UI не оставлять параллельным источником тех же задач;
   его замену выполнять через регистрацию features, сохраняя нужные драйверы.

Готово: обязательная матрица функций покрыта; каждый новый UI соответствует
дизайн-системе IDE. Независимая визуальная проверка отдельным агентом:
исходный запрос, скриншот, baseline и фактический render; существенные замечания
исправлены. Это проверка будущей реализации, для данного плана UI не менялся.

## Этап 4. Данные и совместимость

1. Сохранить исходные данные Minerva и версии их схем; начать с подключения
   к существующему хранилищу либо явного импорта копии, без разрушения источника.
2. Определить source of truth: Minerva хранит исходную историю, OpenIDEA —
   идентификатор и представление задачи; исключить расходящиеся независимые копии.
3. Проверить ветки, вложения, tool pairing, waiting interactions и interrupted
   runs. Исторические исполнения не возобновлять автоматически.
4. Секреты переносить через поддерживаемый secret store; в settings и события
   вывод секретов не включать. Провести тесты чужих session/workspace IDs.
5. Для каждого поддерживаемого режима отдельно проверить auth, доступ к
   проекту, сетевую политику и lifecycle процессов.

Готово: импорт/подключение, повторный запуск и откат проверены на копии данных.

## Этап 5. Переход и обновления upstream

1. Выпустить параллельную сборку на основе OpenIDEA; текущую Minerva сохранить
   до прохождения обязательных сценариев и проверки данных.
2. Проверить обновление fork на следующий upstream-коммит: конфликты,
   protocol drift и регрессии UI. Зафиксировать обслуживание адаптера.
3. После приёмки определить судьбу старого редактора, оболочки и приложения:
   удаление только отдельным изменением с известными потребителями.
4. Не удалять серверные и hosted-возможности как побочный эффект смены desktop.

Готово: воспроизводимый релиз, работающий rollback и понятная процедура
получения обновлений OpenIDEA.

## Проверки и критерии решения

- Базовые проверки upstream из его manifest/CI и профильные тесты изменённых
  модулей; проверка Minerva runtime и протокольных контрактов.
- Fixtures Agent Service и native-драйверов: text/reasoning, tools, allow/deny,
  вопросы, cancel, restart, resume, ошибки и неподдерживаемые capabilities.
- Dirty file против агентной записи, rename/delete открытого файла,
  переключение проектов/worktree, два окна и запоздавшие события старого запуска.
- Большой проект/длинный разговор: tree virtualization, переключение вкладок,
  длительность открытия и отсутствие бесконечного роста памяти относительно baseline.
- Реальный Windows GUI: проводник как в референсе, editor/LSP, focus/keymap,
  разрешения и diff. Build не считается доказательством GUI/runtime.
- Отдельная приёмка browser/remote/hosted только для фактически сохранённых
  режимов; ограничения явно перечисляются перед выпуском.

Точную оценку сроков и объёма дать после этапов 2 и 2б. Сейчас подтверждены
архитектурная точка подключения и подходящая основа, но не совместимость
всех возможностей и не работоспособность локальной сборки OpenIDEA.
