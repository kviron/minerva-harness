# Карта разработки встроенного агента Minerva

Эскиз к [плану MVP](minerva-agent-mvp.md). Пути в таблице без пометки «выделить» существуют сейчас. Предложенные имена обозначают место следующего изменения. Новый crate для каждого блока не нужен. После синхронизации OpenIDEA сверяем карту с обновлённым деревом.

Предпочтение пользователя — использовать готовые механизмы OpenIDEA, Minerva и Rig. Карта описывает обязанности и возможные места выделения кода. До создания нового сервиса проверяем существующего владельца через штатный API, фиксируем недостающую возможность и добавляем минимальное расширение в соответствующем слое. Технические прототипы опираются на текущие механизмы задач, очереди, отмены, сессий и событий.

## Порядок разработки и архитектурное ревью

Работа выполняется отдельными исполнителями по согласованным границам файлов. Общий ревьювер читает карту и вызывающие модули, затем проверяет фактический diff и результаты тестов. Исполнитель исправляет замечания до интеграции. Обновление upstream выполняется в отдельном worktree с сохранением текущих незакоммиченных изменений.

Первый пакет включает обновление OpenIDEA, исправление допуска ReadOnly в едином tool executor и прототип динамического маршрута Rig. Живая проверка политики внедряется как capability существующего владельца настроек. Исполнитель инструмента получает её через сборку зависимостей. Доступ к SQLite остаётся у владельца настроек. Следующие пакеты определяются результатом интеграции и прототипа.

На 24 ноября первый пакет реализован в worktree C:/dev/minerva-openidea-update на ветке codex/openidea-update. В него входит merge стабильной OpenIDEA v0.1.50 с сохранением текущих изменений Minerva. ReadOnly запрещает запись до диалога, live reader ContextService повторно ограничивает допуск после ответа. Существующие Rig model_route/on_model_select подтверждены HTTP-тестом A → инструмент → B. Этот тест подтверждает возможности SDK; production-переключение и durable inbox требуют следующего пакета. Независимое ревью проверило направление зависимостей и единственного владельца допуска. Гарантия актуальности политики относится к допуску handler, уже начавшийся внешний эффект требует отдельного протокола отмены.

Для каждого изменения ревью отвечает на вопросы:

- Кто владеет состоянием, какие входы актуальны, какие являются снимком, и когда происходит эффект?
- Где уже есть нужный алгоритм или константа? Несколько потребителей с одной семантикой используют общего владельца. Параметр отдельной политики остаётся в её модуле. Общий файл констант не становится независимым владельцем всех настроек.
- Есть ли новая обратная зависимость, повторный store, обход публичного API или второй жизненный цикл того же ресурса?
- Что происходит при отмене, повторной доставке, ревокации и ошибке сохранения? Штатная точка входа должна проходить ту же проверку, что и прямой тест модуля.
- Можно ли проверить доменное решение без БД и сети? Сетевые и файловые эффекты выполняются на соответствующей границе.
- UI получает подготовленные данные и callbacks. При сложной подписке или оркестрации controller/hook адаптирует существующий store. Представление занимается отображением и простым локальным взаимодействием. Общие примитивы и токены принадлежат OpenIDEA.
- Какие механизмы другого агента подтверждают решение и какие гарантии нашего хоста требуют отличий?

Лимит строк не заменяет анализ обязанностей. Файл выделяется при появлении самостоятельного владельца данных, алгоритма или эффекта. Фасад и точка сборки зависимостей сохраняются короткими. До интеграции проверяются форматирование, соответствующий линтер, тесты модуля и затронутые вызывающие модули. Runtime и UI подтверждаются в работающем приложении по правилам verify.

### Переход существующих профилей

OpenIDEA сохраняет provider в AgentTask, а Minerva сегодня проверяет префикс модели при загрузке сессии. При переходе сохраняем существующие task ID и session ID. Для сохранённых задач minerva.api.* определяем встроенный движок по виду подключения, включая удалённые из каталога подключения. Маршрут прошлого хода остаётся его атрибутом. При открытии проверяем принадлежность сессии проекту и worktree. Новый доступный маршрут выбирается для следующего хода. Миграция повторяема; повторное открытие старой задачи не создаёт вторую сессию.

Адаптер native/minerva.rs преобразует сохранённые и живые события одной функцией. Для восстановления фиксируем позицию журнала, воспроизводим записи до неё и доставляем последующие записи с устойчивыми ID. Разрыв подписки закрываем дочитыванием журнала. Повторная доставка обновляет уже показанную карточку инструмента. Отмену привязываем к ID запроса или поколению хода в момент её отправки, включая отмену до запуска. Если существующий вызов передаёт только session ID, дорабатываем и отправителя. Получатель проверяет соответствие активному ходу до исполнения отмены.

Сейчас mh-context читает сводку из собственной БД и добавляет её текст в system_prompt. Новый путь читает checkpoint только из session_store. Старый профиль без проверяемой сводки открывается по исходной истории и строит новую сводку при необходимости. Старую БД сохраняем. Сводку помещаем в историю с пометкой происхождения, отдельно от доверенного preamble. Для checkpoint сохраняем ID сессии и ветки, последнюю охваченную запись и ревизию префикса. Публикация проверяет их атомарно. Тест обновления открывает профиль с уже существующей сводкой и проверяет, что в запросе одна копия и она не получила системную роль.

## Точка проверки Rig

В закреплённом rig-agent 0.46.0 драйвер вызывает on_completion_call до сборки запроса. Действующий ProviderStepHook уже читает event.history и event.prompt. RequestPatch.history меняет только предшествующую историю. Свежий результат инструмента может находиться в prompt. Поэтому используем on_completion_call для решения и изменения истории, а on_dispatch для проверки итогового CompletionRequest, включая текущий результат, перед передачей модели. На on_dispatch доступен объект Rig; сериализация в HTTP происходит позже. Избыточный запрос отклоняем через DispatchAction::deny до передачи провайдеру. Проверяем тело запроса на локальном HTTP-сервере с управляемыми ответами. В исходниках Minerva обе точки уже заняты одним hook. Его нынешнее ограничение ответа min(available, 4096) заменяем расчётом маршрута. Смысл этих гарантий проверяем на исходящей записи mock-провайдера до и после обновления Rig, для streaming и обычного ответа.

Вызов суммаризатора выполняется отдельным completion того же маршрута с собственным бюджетом и отключёнными инструментами. Он не проходит рекурсивно через политику сжатия агентского хода. Результат маркируется диапазоном исходных событий. После отмены либо смены ревизии он отбрасывается. Если последний запрос всё ещё слишком велик, сохраняем результат инструмента и выдаём типизированную причину остановки. Один повтор разрешён только для определённо отклонённого модельного запроса при уменьшении его размера. Таймаут с неизвестным исходом и уже начавшийся stream требуют отдельного завершения.

## Бюджет MVP

Предлагаемые ниже числа — стартовые параметры продукта для испытаний. Из возможностей маршрута берём совокупное окно W, отдельный предел входа I и предел выхода O, когда они известны. Явная настройка маршрута может уточнить каталожное значение для custom gateway, в пределах подтверждённых жёстких лимитов endpoint. Только когда неизвестны и W, и I, принимаем рабочее допущение W = 8192; текущий глобальный default 32768 сам по себе не доказывает возможность модели. Если метаданные описывают только независимые лимиты входа и выхода, используем их напрямую, без повторного вычитания выхода из входа.

- Резерв R равен запрошенному маршрутом лимиту генерации, включая reasoning согласно протоколу. Без предпочтения берём min(2048, W/4) при известном или принятом W, иначе 2048. Ограничиваем R известным O. Если выбранный effort и минимальный ответ нельзя вместить, возвращаем причину с предложением изменить effort или маршрут. Адаптер использует тот же лимит в отправляемом запросе.
- Базовый предел B = min(I, W − R) при наличии обоих ограничений. Используем единственный доступный предел, если второй отсутствует. Отрицательный результат означает исчерпанный бюджет. Запас на погрешность при локальной оценке равен max(512, ceil(0.15 × B)), при проверенном провайдерском подсчёте всей формы запроса — max(128, ceil(0.03 × B)). Доступный вход равен max(0, B − запас). Например, для неизвестного текстового маршрута B = 6144, запас = 922, допустимый вход = 5222.
- Для текста, изображений, tool schemas и служебных полей фиксируем источник оценки. Если стоимость изображения оценить нельзя, возвращаем объяснение для этого вложения. При следующем ответе сравниваем оценку с фактическим input usage на том же маршруте, учитывая правила cache/reasoning провайдера. Проверяем русский текст, код, JSON и изображения на маршрутах минимум двух семейств. Эти измерения служат основанием для изменения коэффициентов.

## Пример границ в Rust

Псевдокод показывает интерфейс чистой функции. Exchange описывает группу «вызов и все его результаты», Estimate содержит размер всего предполагаемого запроса. ContextSnapshot содержит неизменяемую ревизию, группы Exchange, обязательный текущий prompt, совместимый checkpoint и оставшихся кандидатов на сокращение. Координатор применяет одно решение и повторяет оценку. Каждая успешная итерация должна уменьшить размер и исчерпать выбранного кандидата. При отсутствии прогресса возвращаем TooLarge. Число сокращений ограничено исходным числом кандидатов, попытка построения сводки одна на подготовку запроса.

```rust
enum ContextDecision {
    Send,
    ShortenToolResults(Vec<EventId>),
    Summarize(HistoryRange),
    TooLarge { required: Tokens, available: Tokens },
}

fn decide(
    snapshot: &ContextSnapshot,
    estimate: Estimate,
    budget: InputBudget,
) -> ContextDecision;
```

Первый вертикальный срез — записанный ответ Rig с вызовом инструмента и большим результатом. Через обычный backend агента проверяем исходящий второй запрос, неизменённую исходную историю и однократное исполнение. Следом добавляем рестарт и смену маршрута, отзыв MCP-допуска, гонку с отменой и конфликт отката. Проверки кода и правила UI берём из основного плана.

Карта расширена [механизмом локальных субагентов](minerva-subagents.md): дочерние сессии, обмен сообщениями, доставка итогов и навигация в OpenIDEA.

Проверка первого пакета: 58 целевых backend-тестов, 126 frontend-тестов (ещё 8 пропущены), полный frontend typecheck и production build, cargo check -p ide-agent --locked, rustfmt и Clippy выбранных пяти vendor-crates с --no-deps прошли. Общий Clippy с проверкой зависимостей обнаруживает прежний too_many_arguments в mh-lsp::query_document. Независимый browser-просмотр подтвердил Agent → Development → Agent; нативное вспомогательное окно и реальная генерация в обновлённом приложении требуют отдельной проверки.

## Второй пакет — непрерывность API-диалога

Реализована смена API-провайдера между ходами через существующий agentSetConfig с option=provider. Нативный адаптер проверяет принадлежность сессии workspace, сохраняет точный старый маршрут и требует явного выбора доступной модели. Удалённое подключение допускает чтение истории через ограниченный прежним префиксом внутренний адаптер. Ошибка восстановления сохранённой Minerva-сессии сохраняет её ID и возвращается пользователю.

Host-координация выделена в crates/ide-agent/src/minerva_routes.rs. Общий gate настроек согласует смену провайдера, приём сообщений и поздние ответы настроек. Проверка маршрута происходит до изменения очереди и истории. Привязка сохраняется до отключения прежнего peer; при ошибке записи routing-поля откатываются. Поколение соединения отделяет уведомления старого клиента. Тесты этого контракта выделены в src/tests/minerva_routes.rs, нативная непрерывность — в native/minerva/session_tests.rs.

Контроллер session/useSessionProvider.ts подписывается на существующий store и обновляет каталог через refreshTaskModels. SessionProviderPicker.tsx получает подготовленные props и использует штатный Select. Composer сообщает о необходимости выбрать модель нового провайдера, сохраняет черновик и блокирует отправку до выбора. Переключение во время активного хода остаётся последующим этапом применения pending route внутри Rig.

Проверка второго пакета: вся библиотечная suite ide-agent прошла (366 passed, 5 ignored), 177 frontend-тестов прошли (ещё 8 skipped), TypeScript, production build с Safari checks, Oxlint, Clippy ide-agent с --all-targets --no-deps -D warnings и cargo fmt --all --check прошли. Независимый Edge-просмотр при 1100×800 подтвердил селектор и баннер через stubDesktop. Нативное окно с новым бинарным кодом и внешние LLM этим просмотром не проверялись. При удалении отдельной модели на фоне устаревшего каталога IDE нативный слой отклоняет запрос до записи в SQLite, а IDE может сохранить попытку как ошибку. Переключение провайдера и отклонение неподходящего маршрута до приёма сообщения покрыты отдельными тестами.

## Контракт настроек мышления для всех API-провайдеров

Каталог возможностей модели сам по себе не подтверждает, что выбранный транспорт умеет передать настройку. Доступные уровни определяет сочетание провайдера, модели, протокола и реализации сериализации. Один адаптер отвечает за список для UI, проверку выбранного значения и преобразование в запрос Rig. UI получает готовые варианты через существующий ProviderView; собственных таблиц семейств моделей в компонентах нет.

Проверенный ориентир DSH: [adapter.ts](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/llm/llm-pi-ai/src/adapter.ts) и [models.ts](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/llm/llm-pi-ai/src/models.ts). Адаптер проверяет точный идентификатор уровня и использует неизменяемый снимок маршрута при подготовке и отправке вызова. Его список зависит от метаданных конкретной модели и таблицы преобразований. Это архитектурный ориентир; наличие записи в DSH не доказывает работоспособность нашего транспорта Rig.

Default означает отсутствие явного переопределения. Off — отдельная возможность, требующая подтверждённого преобразования: отсутствие параметра не всегда выключает мышление. Неподдерживаемое сохранённое значение отклоняется до сетевого запроса; молча заменять его на другой уровень нельзя. При смене маршрута прежний уровень не переносится без проверки.

Приёмка охватывает все PRESETS, оба OpenAI-протокола, Anthropic и Ollama, а также изменённый URL и неизвестную модель. Для каждого предлагаемого уровня проверяем итоговый сериализованный запрос. Отдельно проверяем сохранение служебных заголовков и путей шлюза. Локальные HTTP-тесты подтверждают наш payload; доступность внешнего сервиса и принятие им параметров требуют отдельной проверки с реальным подключением.

Отдельное расширение настроек — явное описание совместимости и уровней для пользовательского шлюза на уровне модели, с наследованием от провайдера. В [config.ts DSH](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/llm/llm-pi-ai/src/config.ts) это reasoningEfforts, compat и modelOverrides. В нашей текущей Provider-схеме таких полей нет: исправление предустановок не означает реализацию этого редактора. До введения проверяемого контракта не угадываем формат неизвестного шлюза по подстроке URL или названию модели.

Текущий срез: модуль mh-providers/src/reasoning.rs проверяет реальные JSON-кодировщики Rig и исключает параметры, которые кодировщик отклоняет или опускает. Для OpenCode Zen/Go отдельный маппинг ограничен DeepSeek V4 через Chat Completions; остальные семейства требуют своих подтверждённых контрактов. Z.AI Coding использует диалект Z.AI с адресом coding. Тестовая матрица охватывает 24 предустановки и четыре значения протокола, а HTTP-фикстуры — Default/Low/High/Max модели deepseek-v4.1-flash на Zen/Go и прямой deepseek-v4-flash с родным thinking-конвертом. 17 тестов mh-providers прошли; внешние аккаунты и API этим прогоном не проверялись.

Дополнительно прошли Clippy mh-providers с --lib --no-deps -D warnings, форматирование и нативный IPC-тест ide-agent known_api_models_report_and_restore_their_reasoning_effort. В последнем используется уникальный ID провайдера с каноническим URL Go: проверены объявление уровней, сохранение High, восстановление сессии и отказ от старого effort у неизвестной модели. Независимая статическая проверка блокеров не выявила. Новое окно Tauri этим срезом не запускалось.

## Третий пакет — выбор модели внутри активного хода

Граница пакета — модели и effort текущего API-провайдера. Завершается уже начатый модельный запрос и пакет его инструментов; перед следующим модельным шагом применяется последний подтверждённый выбор. Переключение самого провайдера остаётся между ходами. Обычная отправка сообщения сохраняет прежнюю очередь OpenIDEA; durable inbox и принудительный steer — следующий самостоятельный пакет.

Единственный источник запрошенной пары model/effort — SessionService. API и проверки выделены в mh-sessions/src/sessions/selections.rs, SQLite-транзакции — в session_store/selections.rs. Миграция v7 сохраняет прежние сообщения и делает резервную копию старого профиля. Неизменяемые ревизии выбора и журнал допусков к модельному запросу хранятся в той же базе. CAS для effort не позволяет запоздалому ответу вернуть прежнюю модель. Модель в SessionInfo отражает желаемый выбор; исходный request_json хода остаётся неизменным. Принятие нового хода не перезаписывает более свежий выбор.

Native-адаптер использует существующий session/set_config_option. Его проекция и валидация выделены в native/minerva/selection.rs. Старый workspace.modelEffort читается только при отсутствии нового состояния. Native prompt включает внутренний liveSelection; обычные headless-запросы без него продолжают выполнять явно переданную стартовую модель. Адаптер mh-agent-loop/src/selection_control.rs связывает сессию и конкретный run, выполняя операции хранения через spawn_blocking. ActiveRun содержит только метаданные жизненного цикла, не второй desired-store. Транзакционная проверка провайдера защищает также от другого подключения к той же сессии.

Сервис провайдеров сохраняет один путь исполнения Rig в execution.rs. routes.rs регистрирует конечный набор моделей стартового провайдера. selection_hook.rs в асинхронном on_completion_call фиксирует одну ревизию и план параметров; синхронный on_model_select читает только этот снимок. route_handler.rs проверяет фактический запрос после остальных hooks: точную модель, effort, лимиты, известную совместимость инструментов и изображений, отмену и актуальность подключения. Повтор effect ID не отправляет второй запрос. Изменённые адрес, протокол, ключ или удалённая модель останавливают следующий шаг без возврата к прежней модели. Новые модели регистрируются со следующего хода.

Журнал фиксирует допуск handler к отправке, а не получение запроса внешним API. Уведомление «Next model request» показывает модель и effort через существующие reasoning-части чата, сохраняется вместе со снимком ответа и не добавляется в rig-v1 или следующий prompt. После незавершённого фрагмента новая вставка запрещена: сохраняем частичный ответ и ожидающий выбор вместо сдвига уже отображённых частей. Реакция отмены или ошибки не запускает инструмент повторно.

При подготовке учитываются известные input/context/output-лимиты выбранной модели. Бюджет reasoning сохраняет полный резерв, вместо обрезания до обычного output cap. После преобразований повторно проверяется полный запрос. Оценка токенов остаётся приблизительной: точная токенизация и переработка compaction относятся к отдельному модулю следующего этапа. Подготовительное сжатие выбирает модель из подтверждённого начального снимка; оно сохраняет свой прежний жизненный цикл и не является шагом нового handler-журнала.

Подписанные и непрозрачные блоки истории адаптирует штатный Rig 0.46 по точным API/provider/model. Проверены исходники completion/history.rs, completion/message/native.rs и путь выбранной модели через operation/completion.rs: другой model использует каноническую историю без прежнего native replay. Отдельный собственный конвертер поверх этого механизма не вводится. Сквозной native HTTP-сценарий этого пакета покрывает OpenAI-совместимый протокол; внешние Anthropic/Responses-подключения требуют отдельной проверки.

На стыке с IDE очищаются model-scoped wanted и отметки config_sent прежней модели. Это применяется также к discovered/pending/reconnect-путям и только для Minerva. Отказ RPC восстанавливает точный прежний набор под проверкой поколения и одной блокировкой состояния. Настройки Minerva согласованы с подключением в порядке setting_changes → connecting; переключение не теряется за стартующим peer. Повторный выбор той же модели сохраняет effort и ревизию. Транзакционная гарантия относится к SQLite: потеря RPC-ответа после commit может оставить прежнее представление хоста до повторного чтения сессии; отдельный протокол подтверждения доставки настроек в этом пакете не вводится.

Проверка третьего пакета: вся библиотека ide-agent — 370 passed, 5 ignored; mh-providers — 27 passed; mh-sessions — 16 passed, 1 ignored; mh-agent-loop — 7 passed; runtime provider_harness/events/run_ownership — 11 passed. Нативный IPC-тест проводит A → блокируемый read-only инструмент → выбор B → выбор C → запрос C, проверяя однократный инструмент, ревизию, сохранённое уведомление и отсутствие уведомления в отправляемом prompt. Отдельно проверены headless без opt-in, откат настроек при отказе RPC, переподключение со старым effort, CAS, миграции, отзыв провайдера и повтор dispatch. Scoped Clippy ide-agent и трёх vendor-crates с --all-targets --no-deps -D warnings, форматирование обоих Rust-workspaces и документации прошли. Два независимых обзора границ модулей и последующее общее ревью завершены без блокирующих замечаний. Окно Tauri с новым бинарным кодом и внешние LLM-аккаунты этим пакетом не проверялись.
