# Встроенный агент Minerva в OpenIDEA

Рабочий план на 24 ноября 2026 года. Сначала обновляем основу, затем проверяем один сквозной сценарий от выбора модели до восстановления чата. Для каждого изменения в обзоре кода фиксируем аналог у другого агента, ограничения этого аналога, владельца состояния в нашей системе и проверку через обычную точку входа. Для меняющегося upstream при реализации закрепляем версию или commit.

### Пять решений для первого рабочего хода

1. **Приём сообщения.** В цикле Pi уточнения читаются между шагами, а очередь последующих сообщений проверяется, когда агент готов завершиться. В Codex уточнение адресуется активному ходу через `expectedTurnId`. Для MVP обычная отправка во время работы остаётся следующим сообщением в OpenIDEA. Защиту от повтора IPC реализуем отдельно: IDE выдаёт один ID на отправку, Minerva атомарно связывает его с сообщением сессии и возвращает прежний результат при повторе. Проверка: потерять подтверждение, повторно доставить ту же отправку, затем отправить тот же текст намеренно с новым ID. В истории должны остаться два пользовательских сообщения. [Цикл Pi](https://raw.githubusercontent.com/badlogic/pi-mono/main/packages/agent/src/agent-loop.ts) · [Протокол Codex](https://developers.openai.com/codex/app-server)

2. **Сборка контекста IDE.** Интеграция Claude Code с VS Code фиксирует выделение для сообщения в очереди в момент Enter. OpenCode определяет область инструкций по каталогам и использует CLAUDE.md как запасной источник при отсутствии AGENTS.md в том же каталоге. В Minerva фиксируем явно приложенный текст, URI, диапазон UTF-16 и ревизию буфера при отправке. Хост определяет допустимые инструкции для worktree, Minerva добавляет их однократно. Проверка: отправить несохранённое выделение в очередь, перейти в другой файл и изменить исходный. В запрос должны попасть исходное выделение и инструкции его рабочей области. [Контекст редактора Claude Code](https://code.claude.com/docs/en/vs-code) · [Правила OpenCode](https://opencode.ai/docs/instructions/)

3. **Базовые инструменты.** OpenCode предоставляет отдельные операции чтения, поиска, правки и shell с разными действиями для проверки разрешений. Claude Code интегрирует просмотр diff с редактором. Для Minerva поиск и чтение возвращают путь и версию материала; правка открытого документа проходит через редактор OpenIDEA с проверкой этой версии. Команда получает cwd задачи, а её результат содержит вывод и код завершения. Проверка без внешнего MCP: найти файл, прочитать его, вручную изменить буфер перед агентской правкой, получить конфликт, перечитать и применить исправление; затем вернуть модели ненулевой код тестовой команды. [Инструменты OpenCode](https://opencode.ai/docs/tools/) · [Интеграция Claude Code с IDE](https://code.claude.com/docs/en/vs-code)

4. **Вопрос и разрешение.** В Codex `serverRequest/resolved` закрывает запрос ввода или разрешения, а `item/completed` отдельно сообщает результат действия. Minerva связывает запрос с сессией, ходом и конкретным вызовом инструмента, когда он есть. Ответ закрывает ожидание один раз; исполнитель заново проверяет текущие права и публикует фактический исход. Проверка: после подтверждения запись завершилась ошибкой. Карточка показывает ошибку записи, запрос подтверждения закрыт, повторная доставка ответа не запускает инструмент. [События и подтверждения Codex](https://developers.openai.com/codex/app-server)

5. **Лимит работы и причина завершения.** OpenCode на последнем разрешённом шаге убирает инструменты и просит текстовый итог. Codex сообщает, будет ли повтор после ошибки, и отдельно публикует окончательный статус хода. В Minerva предлагаем зарезервировать последний модельный шаг под ответ по уже полученным результатам в пределах общего лимита. При недоступности модели показываем сохранённый частичный ответ и причину остановки. Проверка для обоих режимов Rig: модель постоянно запрашивает инструмент, последняя разрешённая генерация идёт без инструментов, счётчик не превышен и в журнале одно завершение. Отдельно проверяем отказ провайдера на последнем шаге. [Лимит шагов OpenCode](https://opencode.ai/docs/agents/#steps) · [Ошибки и события Codex](https://developers.openai.com/codex/app-server)

### Очередь и принудительная отправка

В DSH интерфейс QueueDock предлагает действие steer для ожидающей строки, а агент различает next-turn и next-step. На границе нового хода цикл забирает одно обычное сообщение и накопленные next-step, между шагами — только next-step. steer доставляет уточнение на ближайшую доступную границу шага. Текущий запрос и пакет инструментов завершаются согласно своему жизненному циклу. Документ раннего решения отдельно разбирает гонку между удалением строки и повторной отправкой; актуальный core уже описывает единый durable inbox, поэтому старую transient-модель из заметки не переносим. [Действие в QueueDock](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/client/ui-conversation/src/client/queue/QueueDock.tsx) · [Актуальный контракт inbox](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/docs/subsystems/core.md) · [Разбор гонок отправки](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/.agents/notes/archived/feature/2026-07-30-web-queue-steer-action.md)

Для Minerva определяем поведение MVP:

- Enter во время работы сохраняет сообщение для следующего хода. «Отправить сейчас» переводит выбранное ожидающее сообщение в уточнение текущего хода на ближайшей границе перед модельным запросом. Оно сохраняет текст, вложения и снимок редактора, принятые при исходной отправке.
- Операция выполняется на backend одной командой с session ID, message ID и ожидаемым turn ID. Перевод и захват сообщения координатором согласованы транзакционно. Повтор команды возвращает прежний исход. Если сообщение уже принято, второй экземпляр не создаётся. Если ход успел закончиться, сообщение сохраняет положение в очереди, UI получает этот результат.
- Состояния «в очереди», «ожидает ближайшего шага» и «принято в контекст» различаются. Принятие фиксируется вместе с привязкой к запросу. UI восстанавливает их по одному источнику состояния. Ошибка подготовки модели или отмена до принятия сохраняет сообщение доступным для дальнейшей отправки.
- После приёма уточнения заново считаем бюджет и учитываем pending-модель. Порядок нескольких уточнений соответствует порядку подтверждённого перевода. Принудительная отправка не подтверждает открытый запрос разрешения. Если агент ждёт ответа пользователя, UI показывает это ожидание и сохраняет уточнение до продолжения.
- Cancel в MVP останавливает текущий ход и сохраняет ещё не принятые сообщения, включая уточнения, для следующей явной отправки. Автоматический запуск сохранённой очереди после Cancel блокируется до действия пользователя. После рестарта очередь доступна, побочные эффекты прерванного хода автоматически не повторяются.
- Технический прототип Rig для динамической модели одновременно проверяет доставку уточнения после результатов инструментов и до следующего completion. Уточнение добавляется в каноническую историю один раз, tool-call/result остаются согласованы. Используем возможности драйвера или тот же тонкий адаптер AgentRun, выбранный после прототипа.

Приёмка: двойной клик «Отправить сейчас», завершение хода одновременно с нажатием, захват строки одновременно с переводом, обрыв UI после подтверждения, вложение и несохранённое выделение, несколько уточнений, отмена до приёма, ожидание разрешения и одновременная смена модели. Локальный HTTP-провайдер должен получить каждое принятое уточнение один раз в правильном порядке.

### Смена модели внутри работающего хода

Изучен DSH master на commit 4b399c39a6d1479cd84ca591b4d7c88e24d38a96. AgentModel.select записывает model/selection. Проекция хранит pending и lastUsed, а request/header снимает pending только при совпадении реально использованной конфигурации. preStep заново читает выбор, разрешает инструменты и собирает инструкции. Затем выполняется модельный запрос и пакет вызванных им инструментов. Следующее preStep принимает новую модель внутри того же хода. Уже исполняемый шаг сохраняет свою конфигурацию. Это уточняет прежнее решение Minerva о закреплении модели до конца хода. [Состояние выбора DSH](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/core/agent/src/model-selection.ts) · [Цикл DSH](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/core/agent-loop/src/agent.ts)

Для Minerva предлагаем следующие границы:

- Выбор в UI атомарно записывает selection revision вместе с provider, model и явным effort. В начале каждого модельного запроса координатор берёт последний выбор. Действующий запрос и уже запущенные инструменты завершаются; их результаты сохраняют происхождение. При смене A → B → C до следующего запроса применяется C. Возврат к A до применения не создаёт уведомление о B.
- Перед применением пересобираем проекцию истории, capabilities, tool schemas и бюджет для целевого маршрута. Проверяем доступность credential и поддержку effort. При ошибке сохраняем исходные сообщения и ожидающий выбор, публикуем причину. Запрос к прежнему провайдеру автоматически не отправляем.
- В журнале связываем каждый фактический запрос с selection revision. Позднее изменение в UI не стирается завершением запроса с предыдущей ревизией. Уведомление о применении связываем с ID нового запроса. В чате отображаем его штатной служебной строкой, например «Модель изменена: A → B». Для следующей модели добавляем краткую запись о происхождении предыдущих ответов. Она сохраняет служебный источник. В DSH installModelSelection создаёт сообщение с source.kind=model-selection и form=notice; изменение только effort такого уведомления там не создаёт. Конкретное визуальное размещение в панели размышлений требует отдельной проверки UI. [Генерация уведомления в ядре DSH](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/core/agent/src/model-selection.ts)
- Прототип Rig 0.46 подтвердил готовый API AgentBuilder::model_route и AgentHook::on_model_select. Тест route_switch_tests на двух локальных HTTP-endpoint проходит последовательность A → инструмент → B и проверяет результат инструмента и уточнение в фактическом запросе B. Для интеграции используем эти API. В прототипе уточнение меняет проекцию запроса; сохранение inbox и однократный приём в каноническую историю остаются отдельной задачей координатора. Согласованную перестройку tool schemas и бюджета для нового маршрута проверяем на следующем этапе.
- Во время ожидания повтора после определённого отказа API проверяем pending и отмену до следующей попытки. Новая конфигурация проходит ту же подготовку, число попыток ограничено всем ходом. На изученном DSH retry-серия использует selection текущего шага; это отражено в сообщении об ошибке, а предлагаемое там исправление требует отдельной проверки статуса. [Обсуждение DSH #13698](https://github.com/deepseek-ai/deepseek-harness/discussions/13698)

Приёмка включает смену во время потока, выполнения инструмента и ожидания разрешения, смену effort, быстрые A → B → C и A → B → A, смену в паузе перед retry, меньший контекст назначения и перезапуск с pending. Проверяем фактический HTTP-маршрут следующего запроса, однократное выполнение инструмента и одно уведомление о применённой смене. Если ход завершился без следующего запроса, pending применяется в следующем ходе.

### Дополнительные механизмы DSH для MVP

Повторный обзор выполнен по тому же commit 4b399c39a6d1479cd84ca591b4d7c88e24d38a96.

1. **Дочитывание большого результата.** DSH отделяет решение о сокращении вывода от spill-хранилища, которое сохраняет исходный текст и возвращает непрозрачный locator с инструкцией чтения. В Minerva используем существующее хранение результатов и вложений: сокращённый ответ содержит ссылку на полный материал, размер и признак сокращения. Чтение доступно частями через разрешённый инструмент и проверяет принадлежность сессии. Ссылка переживает restart. Проверка: поиск вернул большой вывод, нужная строка отсутствует в preview; модель дочитывает её без повторного запуска поиска. Если исходник сохранить не удалось, не публикуем успешную ссылку. [Контракт spill DSH](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/docs/subsystems/spill.md)

2. **Завершение дочерней работы.** Shell DSH сначала разрешает значения cwd, timeout и лимита вывода, затем исполняет готовый spec. Его jobs-контракт отличает отмену записи о задаче от подтверждённого освобождения ресурсов. Для MVP Minerva каждая команда принадлежит ходу и получает cancellation. На Windows проверяем остановку дочернего дерева, а на завершении приложения ждём ограниченное время освобождения собственных ресурсов. Если остановку подтвердить нельзя, сохраняем неопределённый исход. Проверка: тестовая команда создаёт дочерний процесс; Cancel, закрытие чата и выход из приложения дают определённый результат для обоих процессов. Отдельная система долгоживущих фоновых jobs остаётся за границей MVP. [Shell DSH](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/docs/subsystems/shell.md) · [Jobs DSH](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/docs/subsystems/jobs.md)

3. **Порядок инструментов и изменение каталога.** DSH запускает явно допущенные параллельные операции ограниченным пулом, эксклюзивные образуют барьер. В Minerva MVP последовательное исполнение — исходная политика, включая неизвестные MCP. Параллельность вводим только для проверенных инструментов без конфликтующих эффектов. Объявление MCP readOnlyHint само по себе её не разрешает. Для каждого запроса сохраняем ревизию объявленных схем, перед вызовом сверяем актуальную регистрацию и права. При отзыве либо несовместимой замене возвращаем связанный с вызовом отказ. Следующий запрос получает обновлённый каталог. Проверка: две правки одного файла, несколько чтений и удаление сервера после получения tool call. [Исполнитель инструментов DSH](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/docs/subsystems/tools.md) · [История объявлений DSH](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/docs/subsystems/llm-streaming.md)

4. **Частичный stream и честное восстановление.** DSH записывает interrupted-якорь с доставленным префиксом ответа и различает завершение потока и запись полного сообщения. Для Minerva задаём последовательность сохраняемых фрагментов и устойчивые ID, из которых восстанавливается частичный ответ. Статус незавершённости передаём следующей модели. Неполный JSON аргументов инструмента не исполняется. Проверка: после видимого текста приходит обрыв, отдельно обрыв происходит внутри tool arguments; после рестарта частичный текст сохранён, ложного успешного завершения и вызова по неполным аргументам нет. Вопрос допустимой потери последних ещё не зафиксированных UI-фрагментов решаем через явный порядок commit → publish и пакетирование записей. [Цикл и сохранение stream DSH](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/packages/core/agent-loop/README.md)

5. **Единственный писатель сессии.** DSH получает write handle до resume и различает append и барьер durability. В Minerva проверяем единственного владельца изменяющего хода для session ID, согласованность SQLite-транзакций и порядок завершения перед shutdown. UI и replay используют сохранённые ID и версии, повторное открытие чата не запускает второй runtime для той же сессии. Проверка: два одновременных resume, ошибка записи на диск и завершение приложения во время публикации результата. Ошибка сохранения не отображается как успешное завершение. Детали владения выбираем с учётом существующего Runs, без второй независимой блокировки поверх него. [Persistence DSH](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/docs/subsystems/persistence.md)

DSH также имеет подменяемые файловые backend и отдельную политику свежести наблюдений. На изученной версии эта политика по умолчанию отключена в dsh-base. В Minerva проверка версии документа остаётся частью контракта правки OpenIDEA. Переносим механизм только после сверки его фактической конфигурации. [Файловая подсистема DSH](https://github.com/deepseek-ai/deepseek-harness/blob/4b399c39a6d1479cd84ca591b4d7c88e24d38a96/docs/subsystems/filesystem.md)

### Пограничные случаи из практики других агентов

Перед первым сквозным тестом с реальной записью проверяем ReadOnly на стороне исполнителя. Переход Ask → ReadOnly во время открытого диалога делает прежнее согласие недостаточным. Проверку повторяем перед побочным эффектом, файл должен остаться в исходном состоянии.

Регрессионные сценарии для существующего адаптера OpenIDEA:

- Удалить прежнее подключение в тестовом профиле, открыть сохранённую задачу minerva.api.* и продолжить через другого провайдера. ID задачи и сессии сохраняются.
- Отсоединить UI после выполнения инструмента, подключить снова во время поступления следующего события. Видны одна карточка с тем же результатом и следующий фрагмент потока.
- Завершить ход A, доставить его запоздалую отмену перед запуском B и отдельно во время B. В обоих случаях B продолжает работу. Ранняя отмена самого B по-прежнему действует.

- DSH сохраняет префикс шлюза при построении URL каталога и учитывает, что ключ записи может быть единственным рабочим ID модели. Проверить tenant URL, заголовки для конкретного протокола, несколько страниц, зацикленный cursor и отмену до последней страницы. Полный результат заменяет каталог атомарно. Публичный каталог сам по себе не подтверждает доступ конкретного ключа. [Разбор discovery в DSH](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/archived/architecture/2026-09-02-protocol-specific-model-listing-discovery.md)
- В Pi исправляли историю, оборванную сразу после tool call. В тесте Minerva инструмент уже изменил файл, но процесс завершился до сохранения ответа. Другая модель получает корректную проекцию неизвестного исхода. После удаления worktree чат по-прежнему доступен для чтения, а запуск инструментов требует подтверждённой рабочей области. [Регрессия Pi](https://upd.dev/badlogic/pi-mono/src/commit/c681d35d765072843ef3490e3a34a08a69f12566/packages/ai/CHANGELOG.md) · [Сессии Claude Code](https://code.claude.com/docs/en/sessions)
- OpenCode проверяет занятость сессии перед откатом. В Minerva проверить запрос отката во время записи, затем завершение хода и безопасный повтор отката при наличии ручных правок. [Реализация revert в OpenCode](https://raw.githubusercontent.com/sst/opencode/dev/packages/opencode/src/session/revert.ts)

## Контракт сжатия

1. Координатор получает версию истории и маршрут назначения. Адаптер собирает запрос с системными инструкциями, объявлениями инструментов, вложениями и текущим сообщением. Оценщик считает вход и резерв ответа с учётом возможностей модели. При неизвестном лимите используется явно заданная консервативная оценка с диагностикой.
2. Политика сжатия получает оценки, границы завершённых обменов, прежнюю сводку и бюджет. Возвращает решение о сохранении хвоста, сокращении старых результатов или подготовке сводки. Это детерминированный модуль. Хранилище, сетевой токенизатор, вызов модели и уведомления UI принадлежат отдельным исполнителям.
3. Сначала сокращаем старые результаты только в проекции запроса. При необходимости координатор запрашивает переносимую сводку с целью пользователя, решениями, выполненными действиями, неопределёнными исходами и открытыми вопросами. Проверяем также бюджет самого запроса на суммаризацию. Сводка сохраняет происхождение фрагментов и не получает полномочий системной инструкции.
4. Перед публикацией повторно оцениваем готовый запрос. Сохраняем checkpoint только при совпадении версии исходной истории. Отмена, ошибка, параллельная правка или смена ветки оставляют действующей последнюю совместимую версию. В UI публикуется событие с ID хода. В метрики попадают оценки до и после, длительность и причина.
5. Проверку бюджета выполняем перед каждым запросом к модели, включая шаг после инструмента. Используем on_completion_call для выбора проекции истории и on_dispatch для окончательной проверки запроса со свежим результатом инструмента. Несжимаемый запрос завершает ход с сохранением исходных данных. Версионный тест проверяет обе точки на фактическом вызове тестового провайдера. После переполнения допустим один повтор отклонённого модельного запроса при доказанном уменьшении. Уже выполненные инструменты повторно не вызываются.
6. Отдельные тесты покрывают несколько параллельных tool calls, оборванную пару, неделимое большое вложение, ошибку суммаризатора, гонку отмены с сохранением и возобновление после перезапуска. Помимо размера проверяем смысл сводки на фиксированной истории с решением пользователя и невыполненной задачей.

Карта файлов, контракты модулей, точки расширения Rig и численная политика бюджета приведены в [эскизе реализации](minerva-agent-structure.md).

## Завершение MVP

Пользователь начинает задачу в режиме Agent, открывает Development для просмотра правки и возвращается в Agent. В обоих режимах OpenIDEA показывает одну задачу и тот же чат Minerva. Проверяем сохранение черновика, активного хода и ожидающего разрешения при смене раскладки. Решение по разрешению исполняется один раз. После перезапуска открываем ту же задачу, меняем API-провайдера и продолжаем переписку. Отдельно проверяем, что соседняя задача в другом worktree сохраняет свой контекст и разрешения.

Каждый этап проходит штатные проверки изменённых частей OpenIDEA. Для frontend это Oxfmt, Oxlint, typecheck и тесты, для Rust — rustfmt, Clippy и тесты. Изменения IPC проходят генерацию bindings. Встроенный агент и headless-запуск проверяются отдельно. Сквозной сценарий на Windows проходит через рабочий UI с реальным переключением провайдера, воспроизводимые ошибки проверяются на управляемых ответах. Перед релизом проверяем отсутствие ключей и содержимого переписки в диагностике. Локальные субагенты и оркестрация доступных движков OpenIDEA включены в расширенный MVP по [отдельному контракту](minerva-subagents.md). Они следуют после приёмки одиночного агента. Перенос сессий внешних CLI и точное возобновление незавершённых побочных эффектов отложены.
